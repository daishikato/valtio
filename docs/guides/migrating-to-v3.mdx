# How to Migrate to v3 from v2

Valtio v3 updates its environment requirements and package layout, removes the deprecated `watch` utility, and makes notifications synchronous.
This guide explains how to update code and tooling affected by these changes.

## Requirements

- TypeScript 5.5 or newer (v2 supports TypeScript 4.5 and newer).
- Node.js 22.12 or newer (v2 supports Node.js 12.20 and newer). Node.js 26 is included in the v3 test matrix.
- React 18 or newer. This was also the declared peer requirement in v2; v3 no longer tests React 16 or 17.
- `WeakRef`. On React Native, this means the New Architecture, which is the default from React Native 0.76. `proxy()` throws without it. The type declarations use `WeakRef` too, so TypeScript's `lib` needs ES2021 or newer, unless `skipLibCheck` is on.

The published JavaScript now targets ES2020 instead of ES2018.
Transpile Valtio in your build if you need to run it in environments without ES2020 support.

## Package and import changes

Valtio is now an ESM package. It no longer publishes a separate CommonJS build.
Use ESM imports when possible; supported Node.js versions can also load the ESM entry points with `require()` from CommonJS.

The package exposes these public entry points:

- `valtio`
- `valtio/utils`
- `valtio/vanilla`
- `valtio/vanilla/utils`
- `valtio/react`
- `valtio/react/utils`
- `valtio/package.json`

The previous `dist/esm` directory is gone; the package is now built with TypeScript instead of Rollup.
Deep imports into implementation files are no longer supported.
Import from a public entry point:

```js
import { subscribeKey } from 'valtio/vanilla/utils'
```

The published files use `process.env.NODE_ENV` directly for development-only checks.
Bundlers usually replace this expression for browser builds.
If you load Valtio in a browser without a bundler, provide `process.env.NODE_ENV` before importing it.

## Removed `watch` utility

The deprecated `watch` utility is no longer exported from `valtio/utils` or `valtio/vanilla/utils`.
For a callback observing one proxy, use `subscribe` and run the callback once yourself if you need `watch`'s initial invocation:

```js
import { proxy, subscribe } from 'valtio'

const state = proxy({ count: 0 })
const logCount = () => console.log(state.count)

logCount()
const unsubscribe = subscribe(state, logCount)
```

`subscribe` does not run a cleanup function returned by its callback.
If your `watch` callback returned one, handle that cleanup separately.

For `watch` callbacks that observe multiple proxies or change their dependencies dynamically,
see [valtio-reactive](https://github.com/valtiojs/valtio-reactive).

## Removed `getVersion`

`getVersion` is no longer exported. The version it returned is internal.

- To check whether a value is a proxy, use [`isProxyObject`](../api/advanced/isProxyObject).
- To check whether a proxy has changed, compare snapshots: `snapshot(state)` returns the same object until something in `state` changes. Alternatively, set a flag in a [`subscribe`](../api/advanced/subscribe) callback.

```js
// v2
const isProxy = getVersion(value) !== undefined
const changed = getVersion(state) !== lastVersion

// v3
const isProxy = isProxyObject(value)
const changed = snapshot(state) !== lastSnapshot
```

## `deepClone` takes an `isRef` function

The second argument of `deepClone` and `unstable_deepProxy` was a function returning a `WeakSet` of objects to keep by reference. It is now a function that takes an object and returns whether to keep it by reference. By default, the objects marked with [`ref`](../api/advanced/ref) are kept.

```js
// v2
deepClone(value, () => keptObjects)

// v3
deepClone(value, (obj) => keptObjects.has(obj))
```

A v2 function passed unchanged returns a `WeakSet`, which is truthy, so every object would be kept by reference.

## `proxy-compare` is no longer a dependency

`useSnapshot` tracks reads with its own code. Functions from the `proxy-compare` package, such as `getUntracked`, `trackMemo` and `markToTrack`, no longer work with the objects that `useSnapshot` returns.

- Instead of `trackMemo(tracked.obj)`, call `trackKey(tracked.obj)` from `valtio/react`. The component then re-renders for any change under `tracked.obj`.
- Instead of `getUntracked(tracked)`, read the proxy, or take `snapshot(state)`.

```js
// v2
import { trackMemo } from 'proxy-compare'
trackMemo(tracked.obj)

// v3
import { trackKey } from 'valtio/react'
trackKey(tracked.obj)
```

proxy-memoize uses the `proxy-compare` package, so if a component depends on the identity of an object from the snapshot that a memoized function returns, directly or inside a new object, call `trackKey` on that object, such as `trackKey(result.child)`.

## `useSnapshot` subscribes to what a component reads

A component re-renders when a value that it read from `useSnapshot` changes, as in v2. v3 subscribes to each key that the component read, so a change elsewhere in the state doesn't wake it.
Most components behave as before. These cases differ:

- **A component that reads nothing doesn't re-render.** In v2, it re-rendered on every change to the state.
- **Replacing an object with an equal one re-renders.** After `state.user = { name: 'Ann' }`, a component that read `tracked.user.name` re-renders, even if the name is the same. In v2, it compared the values that it read. To write only what differs, use [`applyChanges`](../api/utils/applyChanges).
- **A key read in an event handler subscribes until the next change.** Reading `tracked.count` in a callback adds `count` to what the component re-renders for, so it can re-render once more than in v2. Read the proxy in callbacks, as the docs recommend.
- **A descriptor read records whether the key is there, not its value.** `Object.getOwnPropertyDescriptor(tracked, 'count')` re-renders when `count` is added or deleted, not when its value changes. Read the value as `tracked.count`.
- **`ref` keeps what it is given.** A value read from `useSnapshot` is the component's tracking object, so `ref(tracked.item)` stores that object. Wrap `snapshot(state).item` instead.

An object that a component passes on without reading under it, such as an effect dependency, a prop or a `proxySet` member, re-renders the component when anything under it changes, as in v2.

## Getters run on the snapshot

In v2, a snapshot stored the value of each getter of the state. In v3, the snapshot has the getter: each read runs it, with the snapshot, or the object that `useSnapshot` returns, as `this`.

- **A component re-renders for what the getter reads through `this`.** A root getter such as `get total()` no longer makes the component depend on the whole state.
- **Results aren't cached.** A getter that returns an object returns a new one on each read. To cache a result, use [proxy-memoize](https://github.com/dai-shi/proxy-memoize) or [valtio-reactive](https://github.com/valtiojs/valtio-reactive).
- **An error from a getter is thrown when it is read**, not by `snapshot()`.
- **Read the state through `this`.** A getter that reads `state.count` through a closure reads the live state, so a component doesn't re-render for it, and a snapshot doesn't keep its value. In development, such a getter of an object warns once when it runs on a snapshot. A class getter is on the prototype, so it doesn't warn.
- **Setters are left out of snapshots.** Assigning to a getter of a snapshot throws a `TypeError`. Write to the proxy.
- **A change that a setter makes in place is heard once a component has subscribed.** A setter that changes an object that isn't proxied, such as `this.date.setTime(value)`, notifies its key, and a component subscribes when it commits. Such a change made before that, such as in a child's layout effect, isn't seen until the component renders again. Assign a new object, such as `this.date = new Date(value)`.

```js
const state = proxy({
  count: 1,
  // v2: worked, because the snapshot stored the value
  // v3: reads the live state, and warns in development
  get doubled() {
    return state.count * 2
  },
  // v3: reads the snapshot that it runs on
  get tripled() {
    return this.count * 3
  },
})
```

## Notifications are synchronous

In v2, `subscribe` callbacks were batched and called once per microtask, unless `notifyInSync` was passed. In v3, every callback runs synchronously after each change.

- **Callbacks run once per change.** Code that makes several changes and expects one notification should wrap them in [`batch`](../api/advanced/batch). If you prefer the v2 delivery, see the coalescing recipe in [`subscribe`](../api/advanced/subscribe#notifications-are-synchronous).
- **Errors thrown by callbacks are rethrown in a microtask.** An assignment never throws because of a subscriber, and the other subscribers still run. Inside [`batch`](../api/advanced/batch), the errors are thrown from `batch` as an `AggregateError` instead. In v2, these errors were unhandled promise rejections; now they are uncaught errors (the `error` event, or `uncaughtException` in Node.js).
- **The `sync` options are gone.** `useSnapshot` and `useProxy` are always synchronous, so the controlled-input caret workaround is no longer needed.
- **Deleting a missing key doesn't notify.** In v2, `delete state.key` notified even when `state` had no `key`.
- **Native array methods notify once per internal change.** `splice`, `sort` and similar methods make several changes, and each one notifies, so a subscriber can see the array in between. Wrap them in `batch` to notify once, with the final array.
- **A proxy's own callbacks run before its parents'.** When a change notifies a proxy and its parents, the callbacks subscribed to the proxy run first, then those of its ancestors, nearest first. An ancestor reached by more than one path is notified once, at its nearest distance. Ancestors at the same distance have no set order.
- **`useSnapshot` takes a snapshot when it renders**, not on each notification, so a loop of unbatched changes re-renders a component once.

| v2                                              | v3                                     |
| ----------------------------------------------- | -------------------------------------- |
| `subscribe(state, callback, true)`              | `subscribe(state, callback)`           |
| `subscribeKey(state, 'key', callback, true)`    | `subscribeKey(state, 'key', callback)` |
| `useSnapshot(state, { sync: true })`            | `useSnapshot(state)`                   |
| `useProxy(state, { sync: true })`               | `useProxy(state)`                      |
| Several changes, one notification per microtask | `batch(() => { ... })`                 |

Passing the removed arguments is a TypeScript error, and it also throws at runtime.

## Ops are removed

`subscribe` callbacks are called with no arguments, and `unstable_enableOp` is no longer exported. In v2, after `unstable_enableOp()`, a callback received a list of changes, each such as `['set', ['user', 'name'], 'Ann', 'Bob']`.

To find out what changed, subscribe to each object you follow, and compare it with what you saw before, for example with a snapshot:

```js
let prev = snapshot(state.user)
subscribe(state.user, () => {
  const next = snapshot(state.user)
  const keys = new Set([...Reflect.ownKeys(prev), ...Reflect.ownKeys(next)])
  keys.forEach((key) => {
    // a key added or removed with the value undefined is a change too
    if (
      Reflect.has(prev, key) !== Reflect.has(next, key) ||
      !Object.is(prev[key], next[key])
    ) {
      console.log('changed', key)
    }
  })
  prev = next
})
```

To be called only for some keys of a proxy, or for keys being added or removed, pass `keys` or `ownKeys` to [`subscribe`](../api/advanced/subscribe#subscribe-to-keys).

`devtools` names each action after the paths at which two snapshots differ, so a change undone within the same burst is not reported.

## Unsubscribe when you are done

In v2, a proxy that you subscribed to but no longer referenced could be garbage collected together with its callback.
In v3, a subscription keeps its proxy in memory until you call the function that `subscribe` returns.

```js
const unsubscribe = subscribe(state, callback)

// when the subscription is no longer needed
unsubscribe()
```

`useSnapshot` and `useProxy` unsubscribe when the component unmounts.

## Snapshots can't go into state

A snapshot is read-only. In v2, assigning one into state stored it as it was, so later writes to it were dropped without an error.
In v3, assigning a snapshot into state throws, and so does `proxy(snapshot)`. This includes nested snapshots, values read from `useSnapshot`, and values added with `push` or a `proxyMap`'s `set`.
A snapshot of a `proxyMap` or `proxySet` isn't proxied, so it is stored as is, as in v2, and its methods that change it throw.

```
Cannot assign a Valtio snapshot into a proxy. Copy it with deepClone(), merge it with applyChanges(), or wrap it with ref() to store it as is.
```

Copy the snapshot with `deepClone` from `valtio/utils` to change it later, merge it into the state with [`applyChanges`](../api/utils/applyChanges), or mark it with [`ref`](../api/advanced/ref) to keep it as is, for example in a history list.

```js
const tracked = useSnapshot(state)

// v2: stored read-only, so later writes to state.selected are dropped
// v3: throws
state.selected = tracked.items[0]

// v3: copy it to change it later
state.selected = deepClone(tracked.items[0])

// v3: or keep it as is
state.history.push(ref(snapshot(state)))

// v3: or go back to it
applyChanges(state, state.history[0])
```

## Changes in `proxyMap` and `proxySet`

**An object matches its proxy and its snapshots.** In v2, a `proxyMap` matched an object key only with the same object, and a `proxySet` matched an object member with the object or its proxy.
In v3, both match an object with its proxy and with its snapshots. A snapshot marked with `ref` is still only itself.

```js
const tracked = useSnapshot(state)

// v2: false, because tracked.items[0] is a snapshot
// v3: true
tracked.selected.has(tracked.items[0])
```

If a `proxyMap` used an object and its proxy as two different keys, they are one key in v3.

**They notify less often.**

- `set` with the value that the key already has, and `clear` on an empty collection, don't notify. In v2, they did.
- A component that calls a method on a collection read from `useSnapshot` re-renders when what it read changes. For example, `has(key)` re-renders when the key is added or deleted, and `size` when the size changes. In v2, most methods re-rendered on every change to the collection.

**`clear` ends an iteration.** An iteration that is running when `clear` empties the collection ends there. In v2, as with a native `Map` or `Set`, it went on to visit entries added after the `clear`.

**Set operations take an iterable.** `union`, `intersection`, `difference`, `symmetricDifference` and `isSupersetOf` of a `proxySet` took an object that has `forEach` but isn't iterable in v2. In v3, that throws a `TypeError`, so pass a `Set` of its values instead.

## Naming in examples

The docs now typically use `state` for `proxy(...)`, `snap` for `snapshot(state)`,
and `tracked` for `useSnapshot(state)`.
This naming change does not affect the API or require changes to your code.
